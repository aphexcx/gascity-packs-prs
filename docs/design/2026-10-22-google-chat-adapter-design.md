## 1. Purpose

APM's people reach Syndi in Google Chat the way they reach her in Slack today, and she answers in the same thread. She also sits in spaces and listens without being mentioned, chiming in when she can help. The pack is generic: many Gas City cities will use it to talk to their users, so nothing in the code is specific to APM, Bonanza or Syndi.

## 2. Architecture

One pack, `gchat`, in the city repo (`packs/gchat`), built to go upstream later. One long-running process, the adapter, which gc supervises as a `proxy_process` service the way it runs the Slack adapter. It holds the identity's user token and does four jobs:

- **Listen.** One Workspace Events API subscription over all of the identity's spaces: messages created, updated and deleted; reactions created and deleted; memberships created, updated and deleted, plus the batch variants Google sends automatically for each of those (`batchCreated`, `batchUpdated`, `batchDeleted`), which carry several resources in one event. The resource rides in the event, so no extra read is needed. Events land on a Pub/Sub topic. The adapter keeps one persistent streaming-pull connection open to the Pub/Sub subscription, on which events arrive the moment Google publishes them. Chat itself is never polled. Such a subscription lives four hours at most; the adapter renews it ahead of expiry, recreates it if it lapses, and on any gap reads each space's recent history to fill in.
- **Deliver.** Each message becomes a gc inbound turn for the bound agent (the mayor by default): provider `gchat`, the space as the conversation, the Chat thread as the reply target, the sender's name and id, and each attachment named in the message text with its type and local path, because gc renders a turn from the text and not from attachment records. Edits and deletes arrive too. A reaction on one of the identity's own messages is a turn; reactions on other people's messages are recorded for context only. Per space, config says wake on everything or on mentions only, and the adapter counts turns per space.
- **Speak.** gc's outbound publish reaches the adapter and goes out through the Chat API as the identity, in the right thread, split at Chat's size limit, with a request id so a retry never double-posts.
- **Act.** A local command surface for any process on the machine: `gc gchat publish`, `react`, `upload`, `read`, `spaces`, `status`, `auth`, `reply-current`. JEV or a worker can call `react` in a few hundred milliseconds without a mayor turn.

Config lists identities, one entry today (name, agent, token file). A space can be bound to another agent with `gc extmsg bind`. The Google side is: a Cloud project, an Internal OAuth client of the Desktop type, the Chat API configured with an application name, avatar and description and interactive features left off (Google requires that configuration for create, update and delete calls even when the caller authenticates as a user; the configured name is what Chat attributes API writes to), a Pub/Sub topic with a pull subscription, and the identity's account as Subscriber on it. The identity still acts as the user on every call. No public URL; nothing inbound to the machine.

## 3. Components

### Pack layout (`packs/gchat`)

- `pack.toml`: `[pack] name = "gchat"`, `schema = 2`; one `[[service]]` named `gchat`, `kind = "proxy_process"`, `command = ["./adapter/run.sh"]`, `health_path = "/healthz"`, publication visibility private. The adapter binds the Unix socket gc hands it in `$GC_SERVICE_SOCKET`; gc reverse-proxies `/svc/gchat/*` to it.
- `adapter/`: one Go program, `gc-gchat-adapter`, its own Go module. `run.sh` resolves the secrets file (explicit `GC_GCHAT_ADAPTER_ENV`, else `$GC_SERVICE_SECRETS_DIR/env`, else `~/.config/gc-gchat-adapter/env` for standalone runs), sources it, and execs the binary. The binary is built once (`go build`); the pack ships the build step, not a runtime install.
- `commands/<verb>/command.toml` plus a shell wrapper per verb: `auth`, `publish`, `reply-current`, `react`, `upload`, `read`, `spaces`, `status`. Imported into a city under the binding `gchat`, they surface as `gc gchat <verb>`. Every wrapper except `auth` calls the adapter through gc's service proxy and sends the `X-GC-Request` header on any call that mutates; no secret is in a wrapper's environment. `publish`, `reply-current` and `upload` generate an idempotency key before their first request (printed, and accepted back with `--idempotency-key` for a retry), so a retried command never double-posts. A gc callback that arrives without a key (gc permits an empty one) is given a derived key, a hash of the session, conversation, reply target and text, persisted like any other, so an identical retry still returns the existing receipt. `auth` execs the binary's own `auth` subcommand directly: it reads the secrets file itself and works while the service is stopped, because on a fresh install there is no token for the service to start with.
- `city-fragment.toml`: `[[extmsg.default_route]] provider = "gchat" agent = "mayor"`, to be pasted into `city.toml` at setup (the pack parser rejects extmsg keys in `pack.toml`; the include list is legacy). `gc extmsg bind` rebinds individual spaces.
- `README.md`: the Google-side checklist (section 8), setup, secrets, settings, commands, troubleshooting. `CHANGELOG.md`.
- `doctor/gchat/`: a check that the secrets file exists with every required key, the token file is present and refreshes, the subscription is alive, and the route line is in the city config.

### Per-city configuration (none of it in the pack)

Secrets, `<city>/.gc/services/gchat/secrets/env`, mode 600:

```
GCHAT_PROJECT_ID=            # Google Cloud project id
GCHAT_PUBSUB_TOPIC=          # projects/<id>/topics/<name>
GCHAT_PUBSUB_SUBSCRIPTION=   # projects/<id>/subscriptions/<name>
GCHAT_OAUTH_CLIENT_FILE=     # Desktop-type OAuth client JSON from the console
GCHAT_TOKEN_FILE=            # written by gc gchat auth; holds the refresh token; default <secrets dir>/token.json
GC_CITY_NAME=
GC_API_BASE_URL=             # e.g. http://127.0.0.1:8372
```

Optional overrides, used by tests and private deployments: `GCHAT_CHAT_API_BASE`, `GCHAT_PUBSUB_ENDPOINT` (the gRPC endpoint; insecure only when pointed at the in-memory fake), `GCHAT_EVENTS_API_BASE`, `GCHAT_OAUTH_AUTH_URL`, `GCHAT_OAUTH_TOKEN_URL`, `GCHAT_MEDIA_DIR`, `GCHAT_UPLOAD_ROOT`, `GCHAT_STATE_FILE`.

Settings, `<city>/.gc/services/gchat/config.toml`, re-read on change:

```toml
[defaults]
wake = "all"            # or "mentions"

[[identity]]
name = "syndi"          # account_id toward gc; one entry today
agent = "mayor"
token_file = "token.json"   # relative to the secrets dir; omit to use GCHAT_TOKEN_FILE

[[space]]
id = "spaces/AAAA"
wake = "mentions"

[media]
inbound_dir = "<city>/.gc/gchat-media/inbound"
upload_root = "<city>/.gc/gchat-out"
max_bytes = 209715200   # Chat's 200 MB upload limit
```

State, `<city>/.gc/services/gchat/state.json`, written atomically: the subscription's name, expiry and last known state; per space, two recovery cursors, one for messages (by create time) and one for space events (by event time), each marking the end of a history interval that was completely enumerated and handled, never moved by a live delivery, plus pagination progress and the retained catch-up backlog; the transport dedup window (Pub/Sub message ids and CloudEvent ids); per handled message, its revision (last update time, or a deletion tombstone), delivery status (pending, committed, or unresolved with its gc receipt id) and thread; every outbound send intent (idempotency key, parts, request ids, the thread chosen) and its completed receipt; turn counters per space. The file is the delivery ledger and has no second source: Google can rebuild the subscription and space inventory, but not delivery outcomes, multipart progress or acknowledged backlog. So a corrupt ledger, or a missing one where a ledger is expected (the `established` marker in the secrets directory), puts the service into `recovery-required`: the bytes are preserved beside the file, health is degraded with the reason, nothing is acked and nothing new is published, and the service resumes only after a valid ledger is restored from a backup (`gc gchat state restore <file>`) or an operator orders a reset (`gc gchat state reset`), which reports that messages from the gap may be lost or duplicated. A fresh install, with no marker, initializes an empty ledger and sets the marker.

### Adapter units

1. **token**: loads the client file and token file, refreshes, hands out an authenticated HTTP client. `auth` runs the Desktop-client consent on a loopback redirect at the keyboard and writes the token file to a temp file then renames it, so an existing token survives any failure. Its failure paths are explicit: the person cancels (nothing written, exit non-zero); consent denied or granted for fewer scopes than asked (the missing scopes named, nothing written); the loopback listener cannot bind (the port named, retry with another); the token write fails (the error named, the old file kept). The running service watches the token file: when it is created or atomically replaced, the new token is validated with one read call; if valid, the authenticated HTTP and Pub/Sub clients are rebuilt and reconciliation and catch-up resume, which is how `auth` repairs a service that started without a token or lost its credential; if invalid, the previous working credential is kept and the event is logged. Scopes: `chat.messages`, `chat.spaces.readonly`, `chat.memberships.readonly`, `pubsub`.
2. **subscriber**: creates the Workspace Events subscription on target `//chat.googleapis.com/spaces/-` with the eight event types above and `includeResource`, notification endpoint the Pub/Sub topic. Create and renew return long-running Operations; the subscriber waits for the Operation to complete and records the returned expiry, not a computed one. Renewal is scheduled from that expiry with a margin (at three quarters of its life). On any ambiguous failure (a lost response, a renewal error) it gets the subscription and reconciles: an active one is renewed, a suspended one is reactivated once its cause is fixed, and a new one is created only after confirmed absence or expiry (`ALREADY_EXISTS` means get and reuse). Google's own lifecycle events for the subscription, `google.workspace.events.subscription.v1.expirationReminder`, `.expired` and `.suspended`, are handled by a separate dispatcher that gets the authoritative subscription before acting, since such an event can arrive late. There is no reactivation event: reactivation is observed through its Operation and the subscription's state, and catch-up runs after a suspension is recovered as it does after a recreation. When no subscription name is saved (a lost response to the first create), discovery uses `subscriptions.list` filtered by the target and event types.
3. **puller**: one streaming-pull connection to the Pub/Sub subscription; extends the ack deadline while an event is being handled; acks only when every change in the event has reached a terminal outcome (gc reports delivered or no_route, or the change is durably retained locally with a recovery obligation); nacks on transient failure; quarantines a permanently malformed event (acked, kept on disk, counted in `status`) instead of nacking it forever.
4. **inbound**: event to gc inbound message: dedup, own-message skip, wake policy, mapping, attachment fetch, POST to gc.
5. **outbound**: the socket server. `/publish` is gc's callback and nothing else: it performs one Chat send for a `PublishRequest` and never submits anything back to gc. `/commands/publish` is what the `publish` and `reply-current` wrappers call: it resolves the calling session and conversation, and for a bound session submits the text to gc's `/extmsg/outbound` (gc then calls `/publish`), while an unbound caller takes the direct-send path of section 4, step 9. Also `/commands/upload`, `/react`, `/read`, `/spaces`, `/status`, `/state` (restore, reset), `/healthz`.
6. **chat**: thin Chat API client: per-space write queue at one write per second, reaction limit, backoff with the server's retry hint.
7. **state**: the state file, atomic writes.
8. **registrar**: at startup POSTs to gc's `/v0/city/{city}/extmsg/adapters` with the `X-GC-Request` header (gc requires it on every mutation): provider `gchat`, account id = identity name, callback URL = the absolute base `GC_API_BASE_URL` + `GC_SERVICE_URL_PREFIX` (the same way slack-full builds it; gc appends `/publish` when it calls back), capabilities with their PascalCase JSON keys as gc serializes them (`SupportsAttachments: true`, `MaxMessageLength: 32000`), and the reply instructions sessions see: `gc gchat reply-current --conversation-id {conversation_id} [--thread {thread_ts}] --body-file <path>`. Re-registers with backoff whenever gc restarts. Every conversation reference the adapter sends gc, inbound, outbound, receipt or binding, carries `scope_id` = `GC_CITY_NAME`; gc rejects a reference without it.

## 4. Data flow

### Inbound

1. Google publishes each event to the topic: message created, updated or deleted; reaction created or deleted; membership created, updated or deleted; each carrying its space and the resource; or a batch variant carrying several. The puller decodes singular and batch variants alike, expands a batch into one change per resource, tracks each change's outcome separately, and acks the enclosing Pub/Sub message only after every change is terminal. Unknown future event types are logged and acked.
2. **Dedup, two layers.** Transport: Pub/Sub delivers at least once, so state keeps a window of handled Pub/Sub message ids and CloudEvent ids and drops repeats. gc: it deduplicates on the conversation plus `provider_message_id`, and ignores `dedup_key` in this version. So a created message's `provider_message_id` is its Chat message name, the same id history catch-up uses, and every follow-up gets its own stable id: an edit is `<message name>#updated#<update time>`, a delete `<message name>#deleted`, a reaction `<reaction name>#created` or `#deleted` (two users reacting to one message, or one user removing and re-adding, never collide). State keeps each message's revision so a stale event cannot resurrect a deleted or superseded message.
3. The identity's own messages are skipped (gc already holds them as outbound). A message from a bot sender is marked `is_bot`.
4. **Wake policy.** A DM always wakes. In a space set to `all`, every human message is delivered. In a space set to `mentions`, a message is delivered only if its annotations mention the identity's user; the rest go to the adapter's local log, readable with `gc gchat read`. Each delivered message bumps that space's turn counter.
5. **Mapping** to gc's `ExternalInboundMessage`, posted as `{"message": {...}}` to `/v0/city/{city}/extmsg/inbound` with `received_at` set and the `X-GC-Request` header: `provider_message_id` = the Chat message name; `conversation` = `{scope_id: <city name>, provider: gchat, account_id: <identity>, conversation_id: <space name>, kind: dm | room}`; `reply_to_message_id` = the Chat thread name; `actor` = `{id: <user resource name>, display_name: <display name, or the resource name when Chat gives none>, is_bot}` (gc's actor has no email field); `text` = the message text with user mentions rendered as names, followed by one line per attachment: its filename, MIME type and local `file://` path for a file uploaded to Chat (fetched to the inbound media directory), or its Drive link; the same attachments also fill the `attachments` field (`provider_id`, `url`, `mime_type`, the only fields gc has), but the lines in the text are what the agent actually sees, because gc renders a turn from the text alone. An attachment that cannot be fetched (oversize, forbidden, disk full) is reported in its line as unavailable with the reason, and the message is still delivered. gc wakes the bound agent, whose turn shows the conversation `gchat/spaces/…`, the sender, the message id, the thread, and the reply command.
5a. **Delivery outcome before ack.** Before the POST, the change is written to the ledger as an intent with its `provider_message_id`. gc's response carries a delivery status and, when the fan-out is still running, a receipt id, which is persisted at once. `delivered` and `no_route` are terminal: the change is committed and the event may be acked (`no_route` is also surfaced in `status` as a routing problem). `failed` and `partial` are retried with the same identity (the same `provider_message_id`), so gc's own dedup keeps a late duplicate out. `pending` is held and its receipt is polled: gc reports the receipt as `pending` (keep waiting, for up to one hour from the intent, gc's own receipt retention, since gc's receipt store leaves the wait bound to the consumer), `concluded` (read its delivery status and treat it as above), or `unknown` (gc restarted, or the record aged out; concluded receipts are kept for one hour). A 5xx or 429 answer to the POST is gc asking for a retry (gc's inbound route answers 503 while a city is being reloaded): the event is held unacked and the same intent is posted again; a 4xx answer is a definite rejection and becomes an unresolved delivery with the status in its reason, with two refinements from task 10b: a 408 is retried like a 5xx or 429, and a 404 whose code is `city-not-found` (gc answering for a stopped city) is held and retried, while every other 404 stays definite; a 3xx answer leaves the delivery unknown and is recorded unresolved as "gc answered HTTP 3xx; delivery unknown". A concluded receipt whose delivery status is still `pending`, an `unknown` receipt, or a POST whose response was lost becomes a durable **unresolved delivery**: it is kept in the ledger, counted in `status`, and never reposted on the adapter's own initiative, because reposting could duplicate a turn that did land; an operator resolves it with `gc gchat resolve <id> --accept` (treat as delivered) or `--replay` (post it again). A permanently malformed change is quarantined the same way. The Pub/Sub message is acked once every change in the event is terminal or durably unresolved, so Pub/Sub never redelivers what the ledger already owns. This gc version does not let the adapter promise exactly-once across a gc restart or receipt eviction; the promise is no loss, with any doubt surfaced rather than guessed.
6. **Edits and deletes** of a delivered message arrive as short follow-ups in the same thread (`edited: …`, `deleted`) with the ids defined in step 2, the one rule for every id, so no one answers a message that changed. A deletion carries no update time (Google's deleted-message payload has only the name), so the ledger records a tombstone for the message name and ignores any later event for it; an update that arrives before its creation is delivered as the creation under the message name itself, and the later creation event is then a repeat. **Reactions** on one of the identity's messages are delivered as a turn (who, which emoji, which message); reactions on others' messages go to the local log only. The identity knows its own messages from the ids kept in state, with a `messages.get` fallback.
7. **Memberships.** When the identity is added to a space, the space is recorded with the default wake setting. Whether the all-spaces subscription covers a space joined later is confirmed in the first live test (section 8).

### Outbound

8. gc calls `/publish` on the registered callback with `PublishRequest {session_id, conversation, text, reply_to_message_id, idempotency_key, metadata}` and waits at most 30 seconds. The adapter converts markdown to Chat's text formatting (bold, italic, strikethrough, inline code, code blocks, bullet lists, links) and splits into parts of at most 32,000 bytes: on paragraph boundaries first; a paragraph or code block larger than the limit is split at a UTF-8 character boundary, with a code fence closed at the end of one part and reopened at the start of the next, and the fence bytes count against the limit. The parts and their request ids (`<idempotency key>-<part number>`) are persisted before the first call, so a retry sends the same parts with the same ids and Chat returns the existing messages. In a named space the first part is created with `thread.name` = the reply target and `messageReplyOption = REPLY_MESSAGE_FALLBACK_TO_NEW_THREAD`; the thread Chat actually used is persisted and the remaining parts go to it, so a vanished thread yields one new thread, not several. In a DM or an unnamed group chat the reply option is omitted (Chat supports it only in named spaces) and `thread.name` alone is used. One write per second per space, queued; queueing and retries stay inside gc's 30-second deadline. The receipt gc gets back is always an HTTP 200 with a JSON body, because gc discards the body of any non-2xx answer and with it any retry hint: on success `{message_id: <first part's message name>, conversation: <the full reference, scope_id included>, delivered: true, metadata: {thread: <thread name>, parts: "<count>"}}`, every metadata value a string because gc's metadata is a string map; on failure `{conversation: <the full reference>, delivered: false, failure_kind: <one of gc's kinds: transient, rate_limited, auth, not_found, permanent>, retry_after: <integer nanoseconds>}`. gc records a delivered outbound in the conversation's transcript and returns an undelivered receipt to the caller without scheduling a retry of its own, so the caller keeps the idempotency key and retries when it chooses.
9. `/react` adds or removes an emoji on a message name (`reactions.create`; for removal, list then `delete`). `/upload` sends a file from the upload root (`media.upload`, up to 200 MB) and posts it in the thread with optional text. `/read` lists a space's or a thread's messages (`spaces.messages.list`, with a thread or create-time filter), newest last, normalized to the inbound shape. `/spaces` lists the identity's spaces with their wake setting and can set it. `/status` reports subscription state and expiry, last event time, counters, the catch-up backlog, and health. `gc gchat <verb>` wraps each; `reply-current` posts into the conversation the calling session was last woken from, like the Slack pack's. Recording in gc's transcript: a text post from a bound session (`publish`, `reply-current`) goes through `/commands/publish`, which submits it to gc's `/extmsg/outbound`; gc sends it through `/publish` and records it on delivery, so the text is never sent directly and there is exactly one Google send. A direct send that bypasses gc (an upload, or a post from a process with no bound session) first writes a send intent to the ledger (the idempotency key, the parts and their request ids, the target thread), then performs the Chat calls, then persists the completed receipt under the key, and only then calls `/extmsg/outbound` (gc refuses that call with 422 `no active binding` when the calling session has no binding, so a post from an unbound process is reported as delivered but not recorded, with gc's reason, and recording is possible only for a bound session); gc's callback to `/publish` finds the persisted receipt under the same key and returns it without posting again, and a crash between the send and the recording is repaired on restart from the intent. Recording has succeeded only when gc's outbound result (a PascalCase body, distinct from the callback receipt) carries a non-null `TranscriptEntry`; an HTTP 200 with `Receipt.Delivered` true and a null entry means gc delivered but could not write the transcript. A delivered-but-unrecorded send keeps its receipt and is retried for recording under the same key; the command reports delivery and recording separately in every case (no session, a binding that belongs to another session, gc down, transcript write failed).
10. **Catch-up.** After a subscription lapse, a restart, or a gap in the stream, and before the live stream is started, the adapter freezes the recovery interval: for each known space the two cursors from the ledger as the lower bounds, and the current time as the upper bound. The live stream then starts and its deliveries never move those cursors, so a message that arrives live while recovery runs cannot hide the gap behind it. The adapter refreshes the paginated list of the identity's spaces (so a space joined during the outage is included, with an empty lower bound), then for each space reads `spaces.messages.list` from the message cursor minus a one-minute overlap through every page up to the upper bound, and `spaces.spaceEvents.list` from the event cursor minus the same overlap for message updates and deletions and for reactions, which Google keeps for 28 days; the dedup layers absorb the overlaps. Pagination progress is persisted as it goes. Missed human messages are delivered under the wake policy, marked `catch-up`, oldest first. The per-space number 50 is a delivery budget per pass, not a cap: what remains is kept durably as a backlog, shown in `status`, and delivered on the next passes, and a cursor advances only when every record in its interval is terminal or durably unresolved. A gap older than 28 days, or history Google will not return, is reported in `status` and the log as unrecoverable; "never lose a message" holds for what Google still has.

## 5. Error handling

Rule: never lose a message, never post twice, never report healthy when not.

- **Credentials.** Transient refresh failures retry with backoff. A permanent one (consent revoked, password changed, admin removed the app) puts the adapter in `needs-sign-in`: `/healthz` reports it, `gc gchat status` says why, one mail goes to the mayor, nothing is acked meanwhile so events wait at Google. Recovery: `gc gchat auth`, whose new token file the running service picks up on its own (section 3, unit 1). Missing or malformed secrets or settings fail at startup naming the file and key.
- **Subscription.** Renewed with a margin before the expiry Google returned (four hours max). A renewal error or a lost response is ambiguous, so the subscriber first gets the subscription and reconciles (section 3, unit 2): renew if active, reactivate if suspended and the cause is fixed, create anew only on confirmed absence or expiry, and treat `ALREADY_EXISTS` as "get and reuse". Every create and renew waits for its Operation before the expiry is persisted. A clock jump is handled by scheduling from Google's expiry, never from local elapsed time. After any recreation, catch up. Creation failing repeatedly (quota, admin change): back off up to a few minutes and mail the mayor once. If the live test shows the all-spaces target misses a space joined later: a second subscription on the identity's own user for membership events, plus a space-list refresh on each.
- **Pub/Sub.** At-least-once and unordered: the dedup layers handle repeats; edits and deletes apply by update time against the persisted revision; an update arriving before its creation counts as the creation. The ack deadline is extended during handling. Transient stream errors are retried inside the pinned client with jittered backoff capped at 30 seconds (not configurable through its public API); the puller itself reconnects with jittered backoff from one second to a minute on the recoverable codes the client does not retry (ResourceExhausted, Unavailable, Internal, DeadlineExceeded, Aborted, Unknown) and returns only on a fatal code (PermissionDenied, NotFound, Unauthenticated, FailedPrecondition, InvalidArgument), which the app interprets before restarting it: Unauthenticated enters `needs-sign-in`, NotFound marks the subscription gone for the subscriber to reconcile, the rest restart with the same backoff. An event that cannot be handed to gc is nacked and redelivered; Google retains it for days. A permanently malformed event is quarantined, not nacked forever.
- **Chat API.** Per-space queue at the write limit; 429 or quota waits for the retry hint, then backs off; the queueing and retries for one publish are bounded by gc's 30-second callback deadline, after which the adapter returns an undelivered receipt with a failure kind and retry hint. gc returns that receipt to the caller and does not retry on its own; the caller keeps its idempotency key and may resend, which Chat and the persisted parts make safe. A reply to a vanished thread falls back to a new thread, once, for all parts. A 403 on a space the identity left marks the space gone, fails its queue with a clear receipt, and stops delivering from it. A failed upload returns an error naming the file; nothing half-posted. A response lost after Google accepted a message is repaired on retry by the request id.
- **gc.** If gc is restarting, the adapter re-registers with backoff, holds events unacked, resumes. `/publish` is idempotent on the key. The inbound POST's delivery status is honored as in section 4, step 5a.
- **The adapter.** The supervisor restarts it on a crash, and it kills a service that is not ready within five seconds of start, so the socket is bound and `/healthz` answers at once. During initialization, catch-up, or while credentials are missing or revoked, `/healthz` returns 200 with the header `X-GC-Health: degraded` and a reason, which keeps gc's proxy routing open; `/status` is always reachable, and an operation that cannot run yet returns an explicit error instead of hanging. Google connections are initialized asynchronously in this order: load the ledger (or enter `recovery-required`), register with gc, reconcile the subscription, freeze the recovery interval, start the stream, catch up. State writes are atomic (temp file, rename). Media stays under size and disk caps, inside the media directory, no symlinks, fail closed.
- Every failure is one structured log line with space, message id and cause; the counters in `gc gchat status` show whether events flow.

## 7. Platform facts the design relies on (verified on developers.google.com, 2026-10-21)

- A Chat app receives space messages only on mention; hearing everything requires a Workspace Events API subscription. As a user, that needs user OAuth and membership in the space; subscriptions expire and need renewal (four hours max with `includeResource`).
- Reactions (create, list, delete) and `media.upload` are user-authentication only; a bot-only identity can never react or send files.
- The Workspace Events API delivers to a Pub/Sub topic only. `chat-api-push@system.gserviceaccount.com` needs the Publisher role on the topic.
- User-authenticated messages are text only (no cards); max 32,000 bytes; `requestId` makes `messages.create` idempotent; threads by `thread.name` with `REPLY_MESSAGE_FALLBACK_TO_NEW_THREAD`; about one write per second per space and five reactions per second.
- The Chat API must be configured in the project (application name, avatar, description; interactive features may stay off) before create, update or delete calls succeed, even with user authentication; Chat attributes such writes to that configured name. Read-only user-authenticated calls need only the enabled API and an OAuth client. Both names people may see, the Chat API's application name and the consent screen's app name, are chosen with care.
- An External consent screen in Testing issues tokens that die after seven days; Internal does not.
- The Workspace Events API sends batch variants (`batchCreated`, `batchUpdated`, `batchDeleted`) automatically for any subscribed event type; the `spaces/-` target is user-authentication only and covers the spaces the user is a member of (the docs are silent on spaces joined later); subscription create, patch and reactivate return long-running Operations, `subscriptions.get` returns the Subscription itself, and `subscriptions.list` finds existing ones by target; a subscription's lifecycle events are `expirationReminder`, `expired` and `suspended`, with no reactivation event.
- `spaces.spaceEvents.list` returns a space's events (messages created, updated, deleted; reactions; memberships) in chronological order with the resource's current state, filtered by event type and an exclusive `startTime`, for up to 28 days back, with user authentication and the same scopes. `spaces.messages.list` filters by thread and create time, not by a message id.
- gc facts the design is bound to (verified in the gc source on 2026-10-22): every conversation reference needs `scope_id`; registration and inbound are mutations and need the `X-GC-Request` header; the callback URL is absolute and gc appends `/publish`; a publish receipt is `{message_id, conversation, delivered, failure_kind, retry_after, metadata}` with no thread field; gc dedups inbound on conversation plus `provider_message_id` and ignores `dedup_key`; the inbound response carries a delivery status and, for a running fan-out, a receipt id whose record reads `pending`, `concluded` or `unknown` and is kept one hour after it concludes; `/extmsg/outbound` sends through the adapter and returns a PascalCase result whose `TranscriptEntry` is null when the transcript write failed; the idempotency key on a publish is optional to gc; a callback receipt's metadata is a string map, its `retry_after` an integer duration in nanoseconds, and the body of a non-2xx callback answer is discarded; gc has no outbound retry schedule and times the adapter out at 30 seconds; the actor type has `id`, `display_name`, `is_bot` only; a turn is rendered from the message text and attachment records are not shown; a proxy_process service must be ready within five seconds and a non-2xx health answer closes its proxy route.

## 9. Later

- Chat-app features (cards, slash commands, dialogs, link previews). Afik's model (10/22 1:21am): Sterling is both a user and an app in Slack, separate entities but indistinguishable in practice as long as nobody has to choose between two of her. In Chat the same shape holds: one persona with two credentials, not two personas. That naming is decided on the Google side when the app is added.
