CONTRACT v1 READINGS (gp-nn90, the gateway lane; posted on gp-nn90 AND gp-9hf1). These are readings of details the contract (whatsapp-gateway-20261103.md SCOPE item 3) leaves unstated. NONE changes a route, a field or a rule. The fake gateway of gp-9hf1 can pin them now; the gateway README carries them verbatim.

1. TIMES: every time field on the wire is an integer of Unix epoch SECONDS: received_at, expires_at, last_inbound_at, window_closes_at, last_webhook_at. last_inbound_at is the owner's message's own Meta timestamp (clamped to the gateway's clock when Meta's is later), never the receive time, so a Meta redelivery hours late does not stretch the window.
2. INBOX: GET /v1/inbox with no after reads after=0; limit defaults to 100, accepts 1..200 and anything else answers 400. An empty page answers {deliveries: [], cursor: <the after it was given>}. delivery.message carries, by kind: message = Meta's messages[] object exactly as received (type, text/image/audio/reaction/..., context, timestamp, id = the wamid); status = Meta's statuses[] object exactly as received (id = the outbound wamid, status, recipient_id, errors[] on failed); joined = the invite text's Meta messages[] object (its id is the wamid that dedups the redelivery). profile_name is null on a status.
3. ACK: POST /v1/inbox/ack {ids: [positive integers, 1..500]} answers 200 {ok: true}. It drops the listed bodies of THIS city's deliveries and no other. Three ids are each a no-op 200, never an error: an id the cron already deleted, an id an earlier ack already acknowledged (the repeated ack: the contract's deleted-id clause read for the ack's own deletion), and an id of another city. A malformed body answers 400. The gateway keeps a body-less row per acknowledged wamid until the cron (8 days), so a Meta redelivery of an acknowledged wamid is still one row and never a second delivery.
4. SEND: answers 200 {message_id: <wamid>}. Errors are {error: <code>}: 400 bad_request | text_too_long (over 4096 characters: the box chunks); 403 not_bound (to is not bound to this city); 422 window_closed (a text or a reaction outside the window, from the gateway's own check or from Meta's 131047); 409 in_flight (another request with the same idempotency_key is still at Meta: retry it; a claim older than 60 s is taken over); 502 meta_error {meta_status, meta_code} (Meta refused or did not answer: no message_id was recorded, so a retry under the same key sends). The idempotency key is per city, and a repeat answers the stored {message_id} with no Meta call, before the window check (a retry after the close still gets the first answer).
5. READ: POST /v1/read {message_id} answers 200 {ok: true}. It answers 404 not_found when that wamid was never delivered to THIS city, and 502 meta_error when Meta refuses it.
6. MEDIA: GET /v1/media/<media_id> answers 404 not_found for a media id not delivered to THIS city or past Meta's 7-day media lifetime. Otherwise it streams the bytes with Meta's Content-Type.
7. WINDOW: windows[] lists every phone bound to this city: {conversation_id: wa_id, last_inbound_at, window_closes_at = last_inbound_at + 86400 - 120} (both null for a phone that has never written). A free-form send is allowed while now < window_closes_at. Moving the window: a message of every type moves last_inbound_at except type reaction, system or unsupported, which are delivered but do not move it (the conservative reading: a refusal costs a template, a wrong open costs Meta's 131047).
8. ERRORS: 401 {error: unauthorized} on a missing, unknown or revoked credential; 404 {error: not_found} on an unknown route; 405 {error: method_not_allowed}.

THE SPEC'S TEST LINE "a text at t0 plus 23h59 sends" cannot hold beside the frozen 120 s margin (the close is t0 + 23h58m). The gateway tests send at the close minus 1 s, refuse at the close and at 24h01, and the README says so.
